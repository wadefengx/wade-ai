## SIM-001

**变更清单为空、缺失或出错时结果一样，CI 可能漏检**

适用范围：只检查本次变更文件的 lint、构建校验或 CI 门禁。
旧行为基线：文档站的标签校验。缺少变更上下文和确实没有变更，都返回成功，只看构建通过，无法判断校验有没有执行。
相关规则：[验证与回归](../playbooks/verification.md)中「CLI、CI、构建」一行和「常见误判」。完整的验收场景见 [Tags 回归案例](../examples/tags-regression.md)。

### 回顾性整理 · 尝试 1：为了零漏检另写一套变更范围计算（撤回）

- 理由：复审要求不漏检，于是按 CI 事件（push、PR、合并队列）、子模块、容器挂载可见性和大小写不敏感的文件系统，分别计算变更文件。
- 验证前预期：当时无记录。
- 评估上下文：上游文档框架的 SDK 和构建插件，本地单测、镜像构建和 CI。
- 实测：修好：新增和修改的文档缺标签时会失败。未修好：main 构建缺少比较基准时直接失败。新问题：SDK 生产代码增加约 880 行，引入了第一个第三方依赖和只在某个平台运行的 `unsafe` 调用，这些平台代码在镜像构建里根本不会执行；同一次 lint 里，通用检查和标签检查用的是两份不同的文件清单。维护者视角的评审结论是 Request changes。
- 决定：撤回。没有真实站点需要的场景，不为它写代码。
- 迁移判断：作为反例保留。看到「为了不漏检，再写一套平行的范围计算」时，先查项目里有没有现成的清单可以复用。

### 回顾性整理 · 尝试 2：共用一份清单，三种状态分开表达（保留）

- 理由：所有检查共用一份变更清单，只算一次。空清单通过文件显式传入，因为空的环境变量传不进容器。算不出清单时传入错误标记，只有启用了这项检查的站点会失败。
- 验证前预期：当时无记录。
- 评估上下文：同尝试 1，另外在真实构建入口上用隔离的夹具复跑。
- 实测：修好：main 构建的清单为空，检查 0 篇，构建通过；PR 里缺标签的新文档会失败，报错指向源文件；补上标签后通过；旧文档的生成页面能正常打开。SDK 生产代码降到 +141/−18，没有新增依赖；镜像内的测试从约 92 秒降到约 32 秒。未验证：启用了按变更检查的下游站点，还没在它自己的 CI 上跑过。
- 决定：保留。下游站点接入后，用它自己的入口再验证一次。
- 迁移判断：改写后复用。「空、缺失、出错」三种状态分开处理，以及成对的正反例加产物断言，可以直接用。比较基准（merge-base、PR 目标分支变量）取决于 CI 平台，换项目时按那个平台的约定重新确认。
- 换项目复验：在目标项目的真实入口跑四个夹具：清单缺失、显式为空、含无效文档、修正后。再读取一篇旧文档的生成产物。

## SIM-002

**模拟维护者评审没有停止条件，方案先膨胀再收缩**

适用范围：「扮演维护者逐行评审，有问题就修，修完再审」这类循环。
旧行为基线：同一个上游 PR，两天里写了 9 份复审报告，推送了 9 次修复，每一轮都有新发现。「零漏检」和「可维护」两个目标互相冲突，最后由 Wade 裁决。有一条评审意见被编译器报错推翻后撤回。SIM-001 的尝试 1 就是在这个循环里出现的。
相关规则：[评审与修复循环](../playbooks/review.md)。

### 2026-11-27 · 尝试 1：给评审循环加上目标确认、分级和停止条件

- 理由：原来的评审提示里只有「不要有遗留，有问题继续修」，没有停止条件。每一轮新加的边界处理，又成了下一轮的评审对象。
- 验证前预期：下一次规模相当的评审，在 3 轮内结束，或者带着剩余项交给 Wade 裁决。生产代码的 diff 不再出现先膨胀再删回的情况。撤回和延后的意见都留在报告里。如果仍然超过 3 轮，并且原因不是 Wade 要求继续，就说明这次尝试失败。
- 评估上下文：wade-ai 的规则改动，还没在真实项目里用过。
- 实测：待验证。
- 决定：待验证。
- 换项目复验：下一次「扮演维护者评审」的任务结束后，回填轮数、每一轮的生产代码 diff 和停止原因。

## SIM-003

**换 Agent 或 harness 后接不上进度，交接文件被历史淹没**

适用范围：跨会话、换 Agent、换 harness 或模型、等待上游的任务。
旧行为基线：一个多仓库任务的上下文文件有 400 行、55 KB，光「当前状态」一节就有 125 行，里面混着过程细节。工作区的说明还得特意注明「以顶部状态为准，下面的历史授权作废」。Wade 多次问过「其他 Agent 接手时读哪份文件」，也有过开着会话直接说「gpt，你来继续执行任务」的切换。同一个需求经常在 Codex、Claude Code、Copilot、OpenCode 之间先后接力，每次换工具都要重新交代做到了哪里。
相关规则：[接力与交接](../playbooks/handoff.md)、[AGENTS.md](../AGENTS.md)「接力和共享工作区」。

### 2026-11-27 · 尝试 1：项目内一块接力板，接入全局入口，每完成一项写一次

- 理由：新会话需要的是目标、进度、基线、下一步和授权，过程记录只在追查时才用得上。规则挂在各工具的用户级入口上，换工具后就不用重新交代。每完成一项就更新，即使 harness 被突然关掉，最多丢一项。做法参考了 [crashproof-handoff](https://github.com/butterpurse-dot/claude-code-crashproof-handoff) 的心跳和收尾核对，以及 [claude-lane-stack](https://github.com/VKirill/claude-lane-stack) 不超过 40 行的进度模板。
- 验证前预期：以「Codex 改 header → Copilot 改 nav bar → OpenCode 改 footer」为例，每个工具开场不用交代背景，就能说出前面谁改了什么、自己该做哪一项，最后 footer 的改动不会碰前面改过的部分。授权只有一份有效版本。如果某个工具开场时没有主动读接力板，或者还要翻 notes 才知道下一步，就说明这次尝试失败。
- 评估上下文：wade-ai 的规则改动，macOS 本机。
- 实测：在临时仓库里放一块写好「Codex 已改 header」的接力板，Copilot CLI 通过用户级入口加载 wade-ai，开场就说对了上一棒做了什么、自己接 nav bar，也答对了「新开 PR 要先问」。
- 决定：被尝试 2 取代。Wade 指出接力不能只覆盖几个已知工具：这次的做法要求每个工具都接入用户级入口，新工具、没有用户级入口的工具，或者在别人机器上都接不上。用户级入口保留下来，只当作省事的一层。

### 2026-11-27 · 尝试 2：协议写进接力板本身，只依赖文件和 git，三层发现

- 理由：能保证任何 harness 都有的，只有「能读写文件、能运行 git」。所以把接力协议写在 `.ai/CONTEXT.md` 的开头，不依赖 hooks、会话恢复、内置 todo 或 memory 这些各家不同的功能。让 Agent 读到它有三层：开场一句话（任何工具都行），项目指令文件里的一行指针（读 `AGENTS.md` 的工具会自动读到），用户级入口（省事）。任何一层生效就够了。
- 验证前预期（实测前定下，实测后补记）：同一个仓库里连续三棒，每一棒只给一层发现方式，都能找到接力板、完成下一项、commit 并更新进度和日志，而且不碰前面几棒改过的部分。某一棒要人额外交代背景，就算失败。
- 评估上下文：macOS，一个三项任务（header class、nav 加 About、footer 文案）的临时仓库，用 `relay-init.sh` 生成接力板。
- 实测：
  - 第 1 棒，Codex：用户级入口加项目指针，提示词只有「继续做这个项目，这一轮只做一项」。完成 header，commit，更新进度和日志。
  - 第 2 棒，Copilot CLI：加 `--no-custom-instructions`，不加载任何指令文件，只靠开场一句话。完成 nav bar，commit，更新进度和日志。
  - 第 3 棒，Codex：用全新的 `CODEX_HOME`，没有用户级指令，只靠项目 `AGENTS.md` 里的一行指针。只改了 `Footer.js`，commit，三项全部勾掉。它还发现第 2 棒留下的「基线」SHA 落后于实际 HEAD，按 git 更正，并在日志里写明。
  - 暴露的两个问题：「基线」里抄的 HEAD SHA 会过期，因为是先写板再 commit；日志格式没有写进协议，三棒都写成了一行。已改为：基线不抄 SHA，最新提交看 `git log`；协议第 4 步写明每条日志的内容。
  - 评审补出的边界，都已改：
    - exclude 整个 `/.ai/` 会让项目要提交的 `.ai/` 文件被悄悄漏掉，改为只排除接力板和 notes。
    - 接力板不进 git，worktree、新 clone 和云端 Agent 看不到，新建前要先找，必要时用 `git add -f` 提交到任务分支。
    - 「进行中」没有收尾记录时，不能直接判定为中断。
    - 多仓库时，harness 要从工作区目录启动。
  - 没测到的：Claude Code（本机没有登录）、OpenCode 和 DeepSeek Harness（本机没装），以及不能运行 shell 的 Agent。
- 决定：保留。
- 迁移判断：直接复用。协议只依赖 Markdown 和 git，换 harness、换模型、换项目都不用改。
- 换项目复验：在下一个真实的跨工具接力需求里，每换一次工具，先只问「之前做了什么，你接下来做什么」，和接力板对照，记录答对没有；也记录有没有出现过两个 Agent 同时认领同一项的情况。

## SIM-004

**常用工具没有接入入口，项目专用指令全局生效**

适用范围：在新目录里启动 Claude Code、Codex、Copilot CLI、OpenCode 或 DeepSeek Harness。
旧行为基线：只有 Codex 在用户级指令里接入了 wade-ai，Claude Code 没有用户级入口，读不到它。Copilot 的用户级指令里有一个业务仓库专用的门禁（要求运行一个只有那个仓库才有的脚本），还有一条 `applyTo: '**'` 的「每个任务都补 UT、覆盖率 80%」，做文档和评审时也会触发，和「缺少防复发覆盖时补用例」冲突。
相关规则：[README · 接入](../README.md#接入)。

### 2026-11-27 · 尝试 1：README 按工具列出入口，接入后自检

- 理由：入口没有加载，后面的规则都不会生效，接力板也没人读。冲突的全局指令会覆盖 wade-ai 的默认做法。各工具的入口路径参考了 [vvnocode/AGENTS.md](https://github.com/vvnocode/AGENTS.md) 的支持矩阵，并按官方文档核对过。
- 验证前预期：在一个空目录里启动本机装了的工具，问「按 wade-ai，新开 PR 前要不要先问？」，都能回答「要」。业务仓库专用的全局指令这次没有移走，所以 Copilot 在其他目录里仍可能被要求运行不存在的脚本，这一项预计不会修好。
- 评估上下文：macOS，本机的 Claude Code、Codex 和 Copilot CLI 用户级配置。
- 实测：
  - `install.sh` 连续运行两次：第一次写入 Claude 的导入行，建了 Codex、Copilot、OpenCode 和 DeepSeek Harness 的软链；第二次全部显示 ok。Codex 原来的入口先备份再替换。
  - 在空目录里问「新开 PR 前要不要先问」：Codex 和 Copilot CLI 都答「要」，Copilot 能跟随 `instructions/` 下的软链。对照组 Copilot 加 `--no-custom-instructions` 答「无法判断」，说明答对确实是因为入口被加载了。
  - Claude Code：本机没有登录，受阻。OpenCode 和 DeepSeek Harness 本机没装，只建了软链，未运行。
  - 预计不会修好的那一项没有动：业务仓库专用的全局指令仍在 Copilot 的用户级目录里。
  - 后续：接力改为通用协议（SIM-003 尝试 2）后，用户级入口降为三层发现中省事的一层；`install.sh` 也可以带路径参数，接入表里没有的工具。
- 决定：保留 README 里的入口表。专用的全局指令要不要移回各自的仓库，由 Wade 决定。
- 迁移判断：直接复用。各工具的入口路径以官方文档为准，工具升级后复查一次。
- 换项目复验：换机器或换工具后，按 README 的「接入自检」走一遍。

## SIM-005

**Runtime v2 篇幅过长，部分硬规则和工具约定冲突**

适用范围：遇到复杂任务时，按 README 打开 Runtime v2。
旧行为基线：466 行英文，带「Hermes」人设和「AI 组织自主运转」的愿景。硬规则包括：派发子代理必须显式指定模型，主会话不能自己修评审发现，每个任务都要评审再用最强模型终审，修复循环最多 5 轮，进度文件放在 `.superpowers/`。这些和 Copilot、Claude Code 自己的子代理规则冲突，也和 AGENTS.md 里「小改动直接做」的口径不一致。
相关规则：[复杂任务](../playbooks/complex-work.md)。原文已归档到 [archive/runtime-v2.md](../archive/runtime-v2.md)。

### 2026-11-27 · 尝试 1：压缩成一份中文的复杂任务指南

- 理由：复杂任务真正用得上的是：什么时候用、spec 和计划至少要写什么、验证要求、评审、交接和何时停下来问。人设、愿景和模型调度属于具体工具的约定。
- 删掉的内容：人设和愿景；技能目录结构；动态专家的示例；模型分层和「必须显式指定模型」；「主会话不能自己修」「不能并行派发实现子代理」（改为「文件集合不相交才并行」）；每个任务评审加终审、5 轮修复（改为 review.md 的停止条件）；`.superpowers/` 进度路径（改为 handoff.md）；Memory 和自我进化的大段描述（改为 SIM）。「什么能证明什么」的证据表移到了 verification.md。
- 验证前预期：复杂任务只要读一份不到 120 行的文档，就能拿到 spec 和计划的必填项，不再有和工具约定冲突的指令。用了 superpowers 等插件的项目，按插件自己的规则走。如果复杂任务因为缺了某条被删的规则而出错，就说明删多了。
- 评估上下文：wade-ai 的规则改动。
- 实测：待验证。
- 决定：待验证。出问题时在这里追加尝试，再决定要不要恢复。
