# SIM · Self-Improvement Memory

SIM 出自 Google Cloud AI 和宾州州立大学的一篇论文（[arXiv 2611.18856](https://arxiv.org/html/2611.18856v1)，[虎嗅解读](https://www.huxiu.com/article/4907380.html)）。在论文的设定里，一个优化器反复修改 Agent 的 harness，也就是给 Agent 配置的上下文、工具、执行和验收机制。SIM 按反复出现的问题分组，记录每次改动的理由、改动前的预测、实测结果和评估的上下文，下一轮再决定是保留、调整、替换还是撤回。

论文里和日常开发有关的结论：

- 只记录问题和根因时，效果时好时坏；完整的 SIM 在所有对照设置里都更好。所以要连同尝试过的改动、预期和实测一起记，失败的尝试也要记。
- 代码任务上，10 组对照中有 9 组带 SIM 的更好。不带 SIM 的运行误以为继承来的完成门禁是自己第一轮加的，围绕它反复收紧和修补。
- 场景相近时，具体用例的证据可以多参考。基准和模型都换了时，要降低它的权重，但不少机制层面的经验仍能直接复用或改写后复用（论文 Table 8）。

在 wade-ai 里，Agent 读的规则（AGENTS.md 和 playbooks）就是 harness。项目里的规则、测试、CI 门禁和脚本也是。

## 什么时候写

- 同一个根因第二次出现。
- 一次代价大的返工或漏验，比如被 Wade 指出，或者推送后才发现。
- 改了规则、工具、CI、测试框架或 harness，wade-ai 自己的规则也算。
- 同样的做法在另一个项目、模型或环境里结果不同。

一次性的笔误、只和本次任务相关的细节，写进交付说明就够了，不写 SIM。

## 写在哪里

- 项目的记录用项目已有的工程笔记。没有的话，默认放在 `.ai/memory/sim.md`，进不进 git 按项目约定。
- 脱敏后能跨项目用的，整理进 [wade-ai 的 SIM 记录](../memory/sim.md)。不写真实人名、内部链接、客户和账号信息。

## 用旧记录之前

1. 按症状或根因查索引，例如「构建成功但没有验证到目标产物」。
2. 先看旧记录的适用范围和评估上下文（项目、入口、工具版本、模型）和现在差多少。
3. 旧诊断能解释眼前的失败时，从旧诊断开始，不要从头分析。
4. 已经试过且撤回的方向，没有新证据就不要再试。
5. 上下文差别很大时，具体用例的结论只当线索。按条目里「换项目复验」写的步骤先验证一遍，再决定用不用。

## 写一次尝试

1. **改之前**，在条目下新建一个尝试小节，写明理由和验证前的预期：预期会修好什么，哪些旧行为保持不变，什么结果说明这次尝试失败。状态先写「待验证」。预期必须在跑验证之前写进文件，否则就失去了对照的意义。
2. **验证之后**，回填实测：修好了什么，没修好什么，出现了什么新问题，还有什么没验证。附上证据。
3. **决定**：保留、调整、替换、撤回，或继续待验证。已经合进去、后来又撤回的尝试也留着，下次就不会再走同一条路。
4. **迁移判断**，从这四类里选一个：
   - 直接复用：原样适用于别的项目。
   - 改写后复用：机制适用，具体参数或命令要按项目调整。
   - 继承并扩展：在别的项目里作为起点，再往上加。
   - 依赖具体环境：只在当时的平台、版本或配置下成立。
5. **回链**：被改动的规则行末加 `〔SIM-xxx〕`，让读规则的人知道它为什么存在。
6. 补记以前的事时，小节标题写「回顾性整理」，验证前预期写「当时无记录」。

## 在项目里落地：每一棒接力就是一轮

论文里的 RSI（递归自我改进）是一个优化器离线跑很多轮：每一轮改 harness，跑基准测试打分，再决定保留什么。日常开发里没有固定的基准，但结构是对得上的：

| 论文 | 项目里 |
| --- | --- |
| harness | 项目的 `AGENTS.md`、`.ai/CONTEXT.md` 里的「约定」、测试、lint、CI 门禁、脚本 |
| 一轮优化 | 一棒接力：一次 Agent 会话 |
| 评估器和分数 | 项目的测试、回归用例，以及 Wade 的验收和纠正 |
| 优化器修改 harness | Agent 发现反复出现的问题后，改规则、加测试、加脚本 |
| SIM | 项目的 `.ai/memory/sim.md` |
| 换基准、换模型后继续优化 | 换项目，或者从 Codex 换到 Copilot、OpenCode 接着做 |

两份文件分工不同：[接力板](handoff.md) `.ai/CONTEXT.md` 记任务做到哪了，SIM 记规则和检查为什么这样改、效果怎么样。下一棒先读接力板接上进度，遇到相关的问题再查 SIM，避免重走上一棒撤回过的路，也不会把上一棒加的规则当成多余的删掉。

和论文的差别：日常开发的样本少，也没有自动打分，所以不要每一棒都改规则。满足上面「什么时候写」的条件才改，改之前写下预期，下一次出现同类任务时回填实测。

## 模板

```markdown
| ID | 问题 | 状态 | 相关规则 |   ← 文件顶部的索引，每条一行

## SIM-00N

**<反复出现的问题或根因>**

适用范围：<任务、入口、环境>
旧行为基线：<原来的症状、对照版本或证据>
相关规则：<链接>
别名：<合并进来的旧 ID，没有就不写>

### YYYY-MM-DD · 尝试 N：<改了什么>

- 理由：
- 验证前预期：<会修好什么；哪些保持不变；什么结果算失败>
- 评估上下文：<项目、版本、环境、用例、命令；必要时写 Agent 和模型>
- 实测：修好：… 未修好：… 新问题：… 未验证：…
- 决定：<保留 / 调整 / 替换 / 撤回 / 待验证>
- 迁移判断：<直接复用 / 改写后复用 / 继承并扩展 / 依赖具体环境，附一句原因>
- 换项目复验：<在新项目里用什么输入、跑什么、看什么>
```

发现两条记录其实是同一个根因时，合并成一条，旧 ID 写进「别名」，索引里保留旧 ID 并指向新条目。
