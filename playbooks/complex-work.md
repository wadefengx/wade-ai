# 复杂任务

适用场景：跨模块、改公开契约、数据迁移、涉及多个仓库、要多个 Agent 并行，或者预计要跨会话的任务。小改动按 [AGENTS.md](../AGENTS.md) 直接做。

本文件取代已归档的 [Runtime v2](../archive/runtime-v2.md)。〔[SIM-005](../memory/sim.md#sim-005)〕项目或工具自带流程时，例如 spec-kit、superpowers，或者项目自己的 `.ai/`，按它们的流程走，本文件只补缺的部分。

## 流程

```text
摸底 → Spec → 计划 → 分步执行与验证 → 评审 → 交付 → 交接与 SIM
```

规模小的任务可以合并步骤。不能省略的有三件事：验收标准写在动手之前，每一步都有验证证据，完成要以证据为准。

## 摸底

- 读目标仓库的约定、相关的 spec、ADR、架构说明和 SIM 记录。旧记录要和当前代码核对后再用。
- 列出：意图、约束、现有实现、风险和未知项。可以回退的选择，写下假设直接推进。会改变结果、扩大范围或难以回退的选择，请 Wade 决定，等待期间先做不受影响的部分。

## Spec

以下字段缺一不可。可以写进项目已有的 spec 文件，也可以写在 PR 描述里。

- 问题和目标
- 验收标准：可以观察，可以逐条核对
- 不改变的行为和兼容范围
- 约束：版本、平台、依赖、权限
- 影响面：模块、接口、数据，以及受影响的使用方
- 风险和回退方式

写完先自查：有没有 TBD 或含糊的说法，各部分是否互相矛盾，范围能否放进一份计划，有没有可以两种理解的句子。最新确认的决定和 spec 不一致时，先更新 spec，再动手。

## 计划

- 每一步都能单独验证。修 bug 的顺序是：复现 → 最小的根因修复 → 复跑同一用例。
- 写出确切的文件路径，以及每一步依赖前面哪一步、产出给后面哪一步：接口、命令、数据格式。
- 不写占位，比如「补充适当的错误处理」「为上面的代码写测试」。要写到实现的人不用再问就能动手。
- 所有步骤都要遵守的全局约束（版本下限、命名、平台），从 spec 原样抄过来。
- 每一步写明验收：要跑的命令和预期的结果。

## 执行

- 一次只做一个有意义的改动，改完就验证。失败时先分析原因再改，不要连续盲试。
- 同一个问题试了两种修法都没解决，停下来重新摸底，或者带着证据找 Wade。
- 发现计划和 spec 冲突时，不要自己选一边，交给 Wade 决定。

## 并行和子代理

- 只有文件集合不相交、接口已经在 spec 里定好时，才并行。共享的文件只能有一个负责人。
- 给子代理完整的上下文，包括目标、文件、约束、验收命令和停止条件。子代理看不到你的对话历史。
- 子代理报告完成时，看 diff、复跑验证，不直接相信它的报告。
- 用哪个模型、要不要用子代理，按所用工具的约定来。
- 同一个工作区里有多个 Agent 时，遵守 [AGENTS.md](../AGENTS.md) 的「共享工作区」一节。

## 评审和交付

- 交付前对照 spec 逐条核对验收标准，按[验证与回归](verification.md)报告每项的状态。
- 自审或模拟维护者评审时，按[评审与修复循环](review.md)控制轮数。
- 预计要跨会话时，从第一天开始维护[交接](handoff.md)文件。
- 结束时检查有没有要写进 [SIM](sim.md) 的经验：返工、误判、对规则或工具的改动。

## 何时停下来问 Wade

- 被外部条件卡住，又没有能独立推进的工作。
- 计划和 spec 冲突，或者需求有两种都合理的理解。
- 达到评审循环的停止条件，剩下的问题会影响结果。
- 需要的操作在授权以外，见 [AGENTS.md](../AGENTS.md)「授权与沟通」。

其他情况按已经确认的计划推进，不需要每一步都确认。
