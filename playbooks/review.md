# 评审与修复循环

适用场景：Wade 让你站在某位维护者的角度评审 PR、自审较大的改动，或者处理 PR 上收到的评审意见。

这类循环如果没有停止条件，每一轮新加的边界处理都会成为下一轮评审的对象，方案会先膨胀，再被删回来。〔[SIM-002](../memory/sim.md#sim-002)〕

## 开始前

- **范围。** 写清楚这次评审的对象：基线和目标，例如 `base..head`，以及要评审的仓库和目录。
- **评审目标和优先级。** 先确认要的是零漏检、可维护、最小 diff，还是尽快合并。几个目标冲突时，先请 Wade 排序，再开始评审。
- **维护者画像。** 只依据这位维护者在真实 PR 上的评论和仓库的约定来模拟，并在报告里注明是 AI 模拟的评审，不冒充本人。

## 每条发现

| 字段 | 写法 |
| --- | --- |
| 级别 | **阻断**：不修不能合并。**应修**：这轮要处理。**细节**：可选。**问题**：需要作者回答。不确定时标成「问题」，不要标成「阻断」。 |
| 位置 | `file:line` |
| 证据 | 用代码、命令输出或复现步骤证明问题存在。没有证据，只是推测时，降一级处理。 |
| 建议 | 优先删除代码、复用现有实现、缩小范围。新增一套机制要说明是哪个真实场景需要它。 |

## 一轮修复

- 一轮 = 针对全部发现集中修复一次 + 复审。复审只看上一轮的发现和这次修复的 diff，不从头再审一遍。
- 修复时遵守 [Ponytail](../ponytail.md)。如果评审意见要求的方案明显比问题本身更大，先回应说明，再决定改不改。
- 发现被证据推翻时（例如按意见改了，编译器报错），撤回这条发现，并在报告里留下撤回的原因。

## 何时停

满足任一条件就停下，把剩下的项交给 Wade：

1. 本轮复审没有新的阻断项和应修项。
2. 已经修了 3 轮。Wade 要求继续时，最多 5 轮。
3. 同一个根因修了两轮还没解决。停下来给出选项，不要继续换写法。
4. 生产代码的 diff 比上一轮多出 30% 以上，或者引入了新的依赖或平台专用代码。停下来说明是哪个真实场景需要它。
5. 两个评审目标冲突，需要 Wade 裁决。

## 报告

```markdown
## 结论
<能否合并；剩下几项，各自卡在哪里>

## 范围
<repo · base..head · 评审目标 · 模拟的维护者（AI 模拟）>

## 发现
| 编号 | 级别 | 位置 | 问题 | 处理：已修 / 撤回 / 延后 / 待 Wade 裁决 |

## 验证
<修复后复跑的命令和结果，每项一个状态>
```

要回复到 PR 上的内容，先起草，用英文和 Wade 的口吻，由 Wade 发出。
