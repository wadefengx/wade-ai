# 验证与回归

## 开改前

1. 把成功条件写成可观察的结果。Bug 优先复现用户贴出的错误、用例或 CI 入口。能比对时，用相同输入和配置保留目标基线结果。
2. 看项目脚本、CI 工作流和相邻调用方，确定真实入口、预期产物和需要保留的行为。挑最小有效的一组用例，按风险加宽。
3. 只改测试时，保留生产代码原样，按现有契约逐项核对断言和快照改动。覆盖率以项目要求的工具、统计范围和口径为准。比较阈值时确认是全量还是新增代码。

## 改完按影响验证

| 变更 | 优先验证 |
| --- | --- |
| Bug 或行为变更 | 原始复现修前失败、修后通过。检查相同根因的相邻入口。必要时在隔离环境短暂恢复缺陷，确认回归用例确实能抓住它。 |
| API、路由、配置、数据迁移 | 当前输入、历史数据、开关状态、无输入与无效输入按契约表现。检查受影响的消费者、失败后的重试或回退。 |
| CLI、CI、构建 | 用真实命令跑正反例，核对调用到了预期任务。检查退出码、诊断和构建产物。命令退出 0 时确认它实际执行和检查了什么。 |
| 公共包、SDK | 先用本地链接或打包产物在真实消费者上验证。有发布任务时，等可安装版本可用后，在同一消费者安装并复测，再扩大接入。 |
| UI | 用实际预览和当前设计源比对。验证关键交互、内容状态和受影响的旧流程。按场景检查窄屏、主题、键盘和无障碍。 |
| 修测试、覆盖率或 CI | 对着原日志和统计口径复跑。确认测试没有被跳过，验收后检查 diff 中的快照、生成物和配置变动。 |

跑完核心用例后，按影响范围执行项目的 lint、类型、构建、相邻套件和 CI 门禁。结果可比较时绑定同一提交、输入和环境。遇到超时、缺服务或已有失败，先定位原因，完成独立验证，并留下可复跑的命令和条件。

## 怎么报结果

- 记录版本或工作区变更、命令或用例、环境、实际结果。关键点可附 CI 链接、截图、产物路径或日志片段。
- 一项检查一个状态：**通过**、**失败**、**跳过**、**未运行**或**受阻**。跑了部分套件时写明范围。平台、容器或模拟环境如实标注。
- 依赖未就绪时写下「等什么 → 在哪里 → 用什么输入 → 看什么结果」。已完成工作照常交付，依赖恢复后验收保留项。
- 比如「本地单测和生产构建通过，容器里的消费者 smoke 通过。独立扫描任务跳过。线上验证等新版本发布后，用历史链接和新链接各走一遍入口」。
